# 第三轮讨论：关键设计约束确认

## 已达成共识（两轮后）

第二轮已达成 87.5% 共识，分歧点已裁决整合：

1. **Orchestrator 角色** → 独立轻量级编排层（MVP 过渡期基础模型兼任）
2. **共识判定机制** → 证据比对为主，语义相似度为辅
3. **最终裁决者** → 人工裁决，模型只输出结构化分歧报告
4. **Review 自动修复上限** → MVP 默认 2 次，后续引入动态熔断机制

## 🔑 新增关键约束：基础模型可替换性

### 背景

用户指出：这个 MCP 工具会接入到不同客户端（Claude Desktop、Cursor、VS Code、Copaw 等），每个客户端的"基础模型"不同。

**问题：** 不同基础模型的能力差异会不会影响协作效果？

### 设计假设

根据第二轮共识，Orchestrator（基础模型兼任）的职责是：
- 确定性路由
- 状态管理
- 异常熔断
- 归一化输出
- **不做技术裁决**

**假设：** 如果职责边界足够清晰，任何模型都能胜任编排角色。

### 需确认的问题

**问题 1：基础模型的最低能力要求**

如果 Orchestrator 由基础模型兼任，需要定义最低能力要求：
- 是否需要理解 JSON Schema？
- 是否需要做意图识别（任务分级路由）？
- 是否需要归一化多模型输出？
- 不同模型在这些任务上的表现差异会不会影响协作？

**问题 2：能力差异的风险**

如果基础模型能力较弱：
- 可能无法正确路由任务
- 可能无法正确归一化输出
- 可能误判共识状态

这是否需要：
- 定义最低能力门槛？
- 设计降级方案（如能力不足时跳过共识流程）？

**问题 3：设计是否足够"模型无关"**

当前工具设计是否足够简单，让任何模型都能正确调用？
- 工具输入输出是否足够结构化？
- 编排逻辑是否足够确定性（少依赖模型推理）？
- 是否需要把更多逻辑硬编码到 MCP Server 本身？
